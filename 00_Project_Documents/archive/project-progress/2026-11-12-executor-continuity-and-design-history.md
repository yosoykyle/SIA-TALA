<summary>Former #48 standing delivery rule</summary>

### Standing delivery rule — structure first, shared design, connected delivery

Applies to every child and affected shared surface. Each child names its roles, journeys and boundaries and inherits this rule without duplicating it. Preserve existing assignments, product safeguards and the wider delivery order.

1. **Resolve the affected workflow across roles before detailed visual design.** Inventory roles, entry/return paths, screens, dialogs, actions, handoffs, states, record/component variants and differences between documentation and code. Follow each role's output into its consumers, including alternate paths, missing/unusual data, larger lists, post-submission editing, cancellation, loading, failure, stale data and recovery. Inspect the affected journey together; this does not reopen every module.
2. **Require a reason to keep something.** Challenge every journey, screen, field, step, option and stored fact, including existing PRD wording, Issue criteria and code. Prefer the simplest sufficient outcome; propose merging or removing what adds no justified value. Check callers, shared consumers, existing records, security/privacy, institutional authority, meaningful history and applicable retention requirements before removal. Destructive data changes retain their approval boundary. Use owning PRDs, installed-version framework guidance, targeted research and qualified legal/comparable-system sources when they resolve uncertainty; distinguish evidence from assumptions. Rough sketches may resolve structure without investing in a design likely to be removed.
3. **Settle and record the structural decision.** Put a concise Keep / Merge / Remove disposition with a one-line reason for the changed or disputed journeys and information in the owning Issue. Link the existing inventory for unchanged items rather than duplicating a second catalogue. The accepted contract or an explicit owner-approved amendment satisfies the decision gate; obtain any missing material decision before affected visual redesign. Routine implementation choices remain delegated. Within the authorized execution boundary, apply the workflow/data/code cleanup and update each affected authority that no longer matches, keeping product rules in PRDs and live progress/evidence in Issues. Prove the functional path and necessary safeguards before treating its visual finish as complete. Record actual removals and reasons. Unresolved optional decoration must not stall useful working behavior.
4. **Establish and reuse the shared design.** Read DESIGN.md, existing components and supported framework patterns before composing a role. Reuse the shared rules for tables, calendars, buttons, dropdowns, icons, colors, spacing, typography, surfaces, light/dark states, navigation and dialog-versus-page choices. Resolve a missing shared pattern once in its owning layer and document the durable standard; avoid a new style system per role. Customize Filament through supported themes/hooks and keep the public Bootstrap adapter on shared foundation tokens. Preserve the accepted visual direction below.
5. **Build meaningful design changes by role and surface.** Begin with the role most central to the affected handoffs, then reuse its applicable patterns in connected roles; the executor may choose a better evidenced order. Use Impeccable for UI/UX judgment and relevant better-* skills. For prototyping, use the Product Design plugin when available, or equivalent available skills. Inspect/simplify, prototype meaningful new composition or interaction, implement, then render-check the surface and connected role variants. Cover deeper pages, materially changed dialogs, publishing/revision and alternate/recovery branches. When an approved shared pattern already settles composition and behavior, implement directly and verify; another prototype that adds no decision value is unnecessary. A single overview image does not cover distinct tasks. A prototype revealing a structural problem returns to the owning workflow/authority record before affected implementation continues.
6. **Verify comprehension and the connected result.** At first glance, purpose, important facts/state and next action should be evident; return/exit, responsive accessibility and safe recovery remain discoverable. Appearance should be pleasing, consistent and clear; attractiveness never excuses confusing behavior. Check each affected role's work and handoffs as it is built, then make one final proportionate cross-role integration pass for drift. Match checks to changed behavior and shared risk, cover important failure modes, reuse valid evidence and consolidate redundant tests. Mark unverified states honestly. No arbitrary design score, exhaustive state/viewport matrix or repeated full-suite loop is required.
7. **Conserve effort and report useful outcomes.** Bound helper tasks, match capability/effort to the work, and keep one owner for shared edits. Reuse shared design, sufficient research, accepted decisions and valid verification. Report changed Keep / Merge / Remove decisions, removals and their dependencies/data treatment, affected role/surface coverage, reused or new shared patterns, actual checks, owner refinements and remaining limitations. Assign broader discoveries to their owning follow-up; no parallel local backlog or silent scope expansion.

**Agent-independent records.** Responsibilities are described as owner, orchestrator, executor/implementer, helper, reviewer and publication helper. No AI vendor, IDE, named agent or model determines those roles. Model/reasoning selections, session addresses and environment setup belong in task-specific handoffs. Framework and skill names remain where they identify the actual technical dependency or design method. Dated historical attributions and literal evidence paths identify provenance, not permanent workflow instructions.

**Existing work continues.** Reuse accepted contracts, approved prototypes, aligned implementation and valid evidence. This refinement does not restart active or completed work, remove known concerns, change an assignment or grant new execution/release powers. Apply it to unresolved decisions and subsequent changed work; report a genuine material conflict before proceeding.


</details>
