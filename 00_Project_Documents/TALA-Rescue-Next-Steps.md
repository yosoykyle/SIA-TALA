# TALA Rescue Next Steps

## Purpose

This is the active planning surface: it controls issue order, scope, and the one active approved plan contract, not product behavior. It is read after `AGENTS.md` and `TALA-Orchestrator-Protocol.md` in the intake chain. The roadmap table stays compact; the active contract temporarily carries the accepted execution detail until Cleanup. The protocol owns the workflow rules, so do not restate them here.

- **Issue numbering:** the next issue continues from the last ID in `TALA-Local-Linear-Sync-Tracker.md` (or Linear).
- **Sub-slice maps:** when a parent issue is split, the primary records the map here on plan acceptance (ID, one-line purpose, status, and next boundary per sub-slice) and keeps the parent here until every sub-slice is complete. A finished sub-slice is trimmed to a one-line status stub — its delivered detail lives in the git commit message, not here — and the parent is removed once every sub-slice is complete.
- **Active contract:** after plan approval, keep exactly one complete active contract below the roadmap. Replace it only after an approved revision; after successful worker launch mark it and its row `In progress` and set the next boundary to `Verify TAL-XX`; remove it during Cleanup.
- **Resume:** after compaction, interruption, rejected worker output, or stale state, load the accepted plan from the active contract and run the resume checkpoint from the protocol before continuing.

### Active Approved Plan Contract - TAL-94A

**Status and boundary:** Approved; awaiting orchestration. This contract is the sole active detailed plan. Re-run the Ground-Truth Gate before editing and stop if live reality differs.

**Role and user goal:** Registrar and authorized academic staff need a reproducible solver input and a trustworthy CP-SAT result in which every ready demand is scheduled exactly as required or the run returns an honest infeasible/error status. System Super Admin may inspect the fixed profile definition but does not design formulas or disable hard constraints.

**Trigger and action:** An authorized Registrar starts a run for one term after readiness passes. Laravel freezes the selected source records into an immutable, hashed snapshot; the Python service validates that contract, solves it, and returns assignments, native solver status, diagnostics, and transparent objective details. TAL-94A does not publish the result.

**Inputs:** Term operating grid and slot size; ready Scheduling Demands; course/component duration, meeting count, modality, same-faculty and room requirements; section delivery groups; active rooms, capacities and feature keys; faculty qualifications, recurring unavailability and approved term load; calendar blocks; fixed assignments; and the versioned `balanced_v1` profile definition.

**Changed records and outputs:** Add only the bounded canonical fields needed to source the term operating grid and course-component room-feature requirements. Preserve the existing `schedule_runs.input_snapshot` as the immutable profile/input record; do not add profile CRUD merely to duplicate code-defined policy. Output one complete assignment set with per-term score detail, or an honest native infeasible, invalid, unknown, or failure result. No official `section_meetings` publication or revision occurs in this slice.

**UI and manual/digital boundary:** Retain the existing Term, Course Specification/Component, Room, Faculty Load, availability, Scheduling Demand, and Schedule Run surfaces. Add only source-field controls needed for the proven input gaps. Hard constraints and exact weights are read-only; policy values remain editable only in their owning records. Candidate review, correction, override, approval, publication, and revision remain TAL-94B-D. The human selects the term, confirms readiness, and later reviews results; CP-SAT owns combinatorial placement, not institutional approval.

**Authority correction:** Before dependent code, reconcile PRD 06 and PRD 13 with the UI blueprint: replace ambiguous `constraint_set_id`/editable-profile language with a stable profile key and version; make hard constraints immutable; keep policy values in authoritative source records; define one code-owned, versioned `balanced_v1` soft-priority preset; and prohibit a generic constraint builder or arbitrary user-editable scoring weights. The snapshot must record the exact enabled terms and integer weights used. Architecture remains Cloud Run production execution with OR-Tools isolated from Laravel.

**Ground-Truth and simplification verdicts:** Keep the aligned Laravel snapshot/run foundation, room feature inventory, faculty qualification/load records, calendar-event availability source, and Python container seam. Patch the proven gaps: the snapshot lacks a versioned profile and required room-feature input; its day grid is hard-coded; advertised constraints exceed enforced behavior; the Python model permits at-most-one rather than exact demand coverage; load, same-faculty, duration/meeting integrity and score semantics are incomplete; and invented `partial` status obscures native solver outcomes. Use one preset and existing source forms rather than building an enterprise policy editor.

**Benchmark result:** Google OR-Tools confirms native `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `MODEL_INVALID`, and `UNKNOWN` outcomes and integer objective modeling. UniTime confirms the proportionate pattern of immutable requirements plus predefined solver configurations and operator review. The accepted disposition is a complete-feasibility contract with one transparent V1 optimization preset, not arbitrary formula editing.

**Qualified-reference disposition:** The Academico reference has no matching Laravel-to-Cloud-Run CP-SAT contract or TALA scheduling records to adopt. Keep TALA's domain model and existing native Laravel/Filament patterns; do not copy unrelated timetable logic or add a scheduling UI dependency in TAL-94A.

**Accepted implementation checklist:**

1. Apply the authority correction above before finalizing dependent implementation.
2. Add the minimum term operating-grid and course-component required-feature source fields, including existing-form and guarded-import support where those records are already maintained.
3. Version the immutable snapshot contract and include deterministic ordering, profile key/version/terms/weights, authoritative operating grid, room features/requirements, faculty load units, availability, fixed assignments, and all identifiers required for independent validation.
4. Make the Python model require exact coverage for every schedulable demand and enforce duration/meeting count, faculty/room/section overlap, qualification, availability/calendar blocks, load, room type/features/capacity, fixed assignments, and same-faculty requirements.
5. Implement `balanced_v1` using only measurable V1 terms with source data: earlier/non-late blocks, reduced faculty idle gaps, balanced faculty load, and efficient room use. Return term-level score details and do not advertise unsupported preference terms.
6. Preserve native CP-SAT status semantics, reject invalid snapshots clearly, and never convert incomplete assignment coverage into an apparently successful `partial` result.
7. Add deterministic PRD-based feasible, infeasible, edge, and regression fixtures shared conceptually across Laravel contract tests and Python solver tests; then prove the same fixture through the local container HTTP boundary.

**Likely files and surfaces:** `prd_modules/06_cpsat_scheduling.md`, `prd_modules/13_system_admin_reports_audit.md`, `ui_surface_blueprint.md`; one forward migration; `Term`, `CourseComponent`, their existing Filament forms and import paths; `ScheduleSolverSnapshotService`; scheduling readiness/generation tests; `cloud/scheduler-solver/tala_solver/solver.py`; solver fixtures, sample payload, tests, README, and Docker build context. Preserve unrelated scheduling ingestion, candidate-review, publication, revision, notification, audit-report, and credential code.

**Verification:** Prove `APP_ENV=testing`, MySQL, and `test_tala_db` before DB-backed checks. Run new/focused Laravel snapshot, readiness, import, dispatch, and scheduling regression tests; Python `unittest` in a recreated disposable virtual environment using pinned requirements; Pint after PHP edits; focused PHPStan/Larastan; the complete PHPUnit suite because the snapshot contract is shared; `git diff --check`; and a local Docker build plus `/health` and deterministic `/solve` smoke matching direct Python results. Docker failure or unavailable startup is reported honestly and is not replaced by an unapproved live-cloud call.

**Human-only step:** If Docker Desktop cannot be started non-interactively, the user starts it and confirms the engine is running. This is manual because it is a local desktop application; successful image build, health response, and fixture solve provide the evidence that unlocks TAL-94A acceptance.
